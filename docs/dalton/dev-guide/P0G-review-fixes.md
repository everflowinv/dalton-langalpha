## 0. 这一轮最重要的一节：不要重犯旧 Dalton 的错误

### 0.1 旧 Dalton 错在哪

旧 Dalton 两个月里，每发现一个漏洞就补一条正则、一条规则、一道校验。规则越来越多，正确的研究也越来越容易被误伤；误伤之后再补例外规则，循环往复。最后测试有一万六千多项，研究却卡在各种校验上走不动，正式成果是 0。

这次审查里已经出现了同样的苗头：

| 现象 | 如果按旧思路修 | 本轮的修法 |
|---|---|---|
| 数字核验只比数字和期间、不比指标，编造数字被放行（R4-1） | 再加一张指标别名表、再加窗口规则 | 由便宜的 LLM 判断"这段原文是否支撑这个说法"，代码只核对数值换算和原文引用是否真实存在 |
| 单位写在表头的标准表格被误判为不通过（R4-4） | 再写一套表头解析规则 | 把表格上下文交给 LLM 标注单位；代码只做换算 |
| "三成""翻倍"这类写法完全没被抽取（R4-8） | 再加中文数字正则 | LLM 标注器本来就能识别，接上即可（`maybe_label_prose_figures_with_llm` 已写好但从未调用，R4-7） |
| 知识写入时字段名写错，每次都被拒绝（R5-5） | 再加一条字段校验报错 | 先改对字段名；以后同类错误由 LLM 自动修复后重试，修不好也只是提醒，不丢写入内容 |
| 探针的规则读错字段，新公告永远唤醒不了分析师（R5-2、R5-6） | 补齐六个探针各自的状态机 | 精简为少数几个确定性信号；"新内容值不值得叫醒分析师"交给便宜的 LLM 分诊 |

### 0.2 本轮的七条原则

1. **确定性代码只管三件事：** 钱（预算、计费、不重复付费）；凭据和权限；数值和单位的换算、算术、编号是否存在。这三类必须写死、必须准确。
2. **语义判断交给 LLM，可以用便宜的模型。** 例如：这句话说的是哪个指标和期间；这段原文能不能支撑这个数字；这条新公告和 thesis 有没有关系；写错的字段该改成哪个字段。每次调用：
   - 要求结构化输出（JSON schema）；
   - 代码再核对一遍可以核对的部分，比如 LLM 引用的原文是否真的出现在来源里、数值换算后是否相等；
   - 失败或超时时，退回保守的处理：标为"未能判断"，交给人看，**不卡住研究**。
3. **校验不通过时，先修复，再提醒，最后才拒绝。** 只有涉及钱、凭据、三条硬规则的才会直接拒绝。
4. **草稿永远不卡。** 只有正式发布时卡一次；即使在发布时，**LLM 拿不准的情况交给 PM 决定**，不由代码一刀切。
5. **不新增次数限制。** 包括"每天最多 N 次""失败 N 次停用"这类，一律不允许。
6. **测试只锁定修好的回归，以及钱和凭据相关的契约。** 每个修复先用真实运行验证（见每步的"验证方式"），再写最少量的测试锁住。**不允许为了让测试变绿而写测试。** 例外只有一个：G2 加一个"所有接口的引用都能解析"的守门测试。
7. **删除优先于补丁。** 一个功能如果设计复杂、长期没有消费方、又不影响研究，就删掉或推迟，不要修补。本轮明确删掉或推迟的见 §8。

### 0.3 统一的"LLM 辅助"工具

为了让第 2 条原则落地，先建一个公共工具，所有用到 LLM 判断的地方都通过它调用，不要各自写调用代码。

**新建 `src/dalton/llm/assist.py`：**

```python
async def assist_json(
    task: str,                 # 任务名，用于日志和缓存，如 "audit.judge"
    instructions: str,         # 给模型的说明（中文即可）
    payload: dict,             # 输入数据
    schema: dict,              # 要求的输出 JSON schema
    *,
    user_id: str,
    role: str = "assist",      # 模型角色，见下
    timeout_s: float = 60,
) -> AssistResult:             # ok / data / error / model / cost_usd / cached
```

- **模型角色 `assist`：** 在 `agent_config.dalton.yaml` 里新增，默认用便宜的模型。首选订阅类、不需要工具的模型，例如 Antigravity 的 Gemini Flash，这样现金成本为 0；备选 `deepseek-flash`。由 `role_policy` 校验。
- **计费：** 一律经 G1.3 的服务端调用包装（准入、预留、记账），不能绕过预算。
- **缓存：** 按 `task + 输入的 hash + 模型` 缓存结果，同样的输入不重复付费。缓存存 Postgres，放在 G1.3 的调用日志表里。
- **失败：** 超时、解析失败、额度用尽，一律返回 `ok=False`。调用方必须有保守的退路，**不能因为 LLM 失败而卡住研究**。
- **日志：** 记任务名、模型、耗时、费用，不记完整输入。

**预估工时：** 1 天。

## 2. G1 预算绕过（最优先）

对应：R2 问题 1、2、3、5、6、7；R2 的"自动任务按用户级判断是否自带 key"变体；P0N.6、P0N.7。

**目标：** 所有花现金的调用都计入日额度，没有任何无上限的入口。

### G1.1 现金按单次调用计算，去掉"整轮放行"

**问题：** 主模型用 OAuth 订阅登录时，整轮对话被当作"自带 key"，准入检查直接跳过（`src/dalton/budget/gate.py:64`），运行中的额度检查也无条件放行（`src/dalton/budget/port.py:69-76`，上限设成"已花 + 100 万 credits"）。同一轮里用现金的子智能体，比如跑 grok-4.7 的 `dalton-evidence`，共用这一条额度租约，完全不受日额度限制。**默认配置下就会触发。** 而且这个行为还被一个单元测试锁成了预期行为（`tests/unit/dalton/test_budget_port.py:48-53`）。

**改动文件：**
- `src/dalton/budget/port.py`：去掉 `if byok:` 的无条件放行分支
- `src/dalton/budget/gate.py`：准入不再因 `byok` 跳过
- `src/dalton/database/budget.py`：结算和汇总的 SQL 改按单次调用的计费类型计算现金（新建 SQL 函数 `dalton_cash_usd`，见 P0N.6）
- `tests/unit/dalton/test_budget_port.py`：**删掉锁定错误行为的那个测试**，改为锁定新行为

**做法：**
1. **现金的定义：** 计费类型为 `platform` 或 `byok` 的调用都算现金；`oauth`（订阅）的调用不算现金，另记名义成本。计费类型来自 `conversation_usages` 里每次调用的 `billing_type`。
2. **准入：** 每轮开头一律检查剩余的现金额度。现金额度用完时，**整轮拒绝**，即使主模型是订阅。这是 P0N.6 已经说明的取舍（决定 L24）：每轮开头还不知道这一轮会不会派出现金子智能体。以后如果你想让纯订阅的对话照常可用，再改成按调用检查。
3. **运行中：** 每次在模型调用的边界检查时，按"本轮已经发生的现金花费"判断，不再因为租约标了 `byok` 就放行。

**验证方式：**
- 本地设日额度 $1。主模型用 Claude 订阅，派出 grok-4.7 的取证子智能体，让它连续读几份长文档。观察：花费到 $1 左右时，下一次现金调用被拒，运行暂停，并显示额度用完的卡片。
- 同一天再发起一轮，在准入时被拒，文案说明"现金额度已用完"。

**验收标准：** 以上两点都满足；`test_budget_port.py` 不再有放行用例；超出额度的部分不超过一次调用的花费。

**工时：** 1.5 天。

### G1.2 设置页里填的现金 key 也要计入

**问题：** 在设置页以"自带 key"方式填的现金 key（比如 xAI），计费类型是 `byok`，上游只把 `platform_cost` 计入 `total_credits`（`src/server/services/persistence/usage.py:146-148`）。所以这些真实的现金花费在预算里永远是 $0。

**做法：** G1.1 的 `dalton_cash_usd` 对 `byok` 行取实际费用（`total_cost`），不再依赖 `total_credits`。同时在设置页的预算卡片上注明："设置页填的 key 同样计入现金额度"。

**验证方式：** 在设置页填 xAI key，跑一次 grok-4.7 对话，预算卡片上的"今日已花"随之增加。

**验收标准：** 同上。

**工时：** 0.5 天。

### G1.3 服务端的一次性调用也要过预算

**问题：** 审稿、数字核验的 LLM 标注、标题生成等，走的是服务端的 `LLMService.complete`（`src/dalton/publish/review.py:241-254`、`src/dalton/publish/audit.py:95-103`）。它不写用量记录，也不经过准入和预留，花费对预算完全不可见。P0N.7 原本要解决这个问题，但还没有实施。

**改动文件：**
- 新建 `src/dalton/llm/complete.py`：`dalton_complete(...)`，所有 Dalton 自己的服务端调用都经它发出
- 新建迁移 `d007_llm_call_journal`（Dalton 迁移链）：调用日志表
- `src/dalton/publish/review.py`、`src/dalton/publish/audit.py`：改为调用 `dalton_complete`
- §0.3 的 `assist_json` 也建立在它之上

**做法：** `dalton_complete` 做四件事：
1. **准入：** 剩余现金额度不足就拒绝，并返回明确的原因；
2. **预留与结算：** 和对话轮次用同一套预算账目；
3. **记账：** 写一条用量记录，计费类型照实填写；
4. **不重复付费：** 按"调用方给的 ID，或请求内容的 hash"查调用日志：
   - 已完成的，直接返回保存的结果；
   - 还在进行中、或进程崩溃后状态不明的，返回"状态不确定"，**不自动重发**，由调用方决定；
   - 失败且没有任何输出的，允许重发。

上游的标题生成、memo 元数据等调用，不在 Dalton 的代码里，**本轮不改**。它们的花费很小，在 §8 里登记为已知遗留。

**验证方式：** 日额度用完之后点发布，审稿返回"额度不足"，不调用模型；额度充足时，审稿的花费出现在预算卡片上；同一份草稿重复审稿，第二次直接返回缓存结果，不产生费用。

**验收标准：** 同上；调用日志表里能看到每一次调用。

**工时：** 1 天。

**验证方式：** 起后端后，对 7 个接口各 `curl` 一次，都返回 2xx 或业务上合理的 4xx。

**验收标准：** 同上；守门测试存在并通过；故意把一个函数名改错，守门测试会失败。

## 4. G3 发布闸门与迁移编造

对应：R4 问题 1–8、9、10、13；R7 问题 1、8、9、11。

**目标：** 编造的数字进不了正式成果，同时正确的报告不会被误伤。发布闸门有三道防线：数字核验、独立审稿、PM 审批。审查发现**三道各漏一处**，必须一起修。

### G3.1 数字核验改为"代码抽取 + LLM 判断 + 代码复核"

**问题：**
- **漏放（严重，R4-1）：** 和来源正文匹配时只比数字和期间，不比指标；数字还是按字符串比较。实测：草稿写"3Q26 DAP 达 512 百万"（真值是 3.2bn），被匹配到一段写着"广告收入 512 亿美元……3Q26"的来源上，放行了。
- **误伤（高，R4-4）：** 单位写在表头的标准表格，单元格的单位判断出错，正确的表格全部"未核实"，发布被卡住。
- **漏抽（中，R4-8）：** "三成""翻倍"这类写法完全不会被抽取，直接绕过核验。
- **误抽（中，R4-6）：** SEC 的 accession 号、带连字符的文档编号被当成数字抽出来。
- **LLM 标注器写好了却没接上（中，R4-7）：** `maybe_label_prose_figures_with_llm` 从未被调用。

**改动文件：** `src/dalton/publish/{numbers.py, match.py, audit.py}`。

**做法：**

1. **抽取（代码）：** 保留现有的抽取逻辑，它对大多数正文写法是准确的。只改两处：
   - 用正则屏蔽 SEC accession 号（`\b\d{10}-\d{2}-\d{6}\b`）和连字符编号，不再当成数字；
   - 解析表格时，把行表头、列表头里的单位词和币种一并交给单位判断，这是一处很小的改动。

2. **标注（LLM，接上现成的函数）：** 在 `extract_figures` 之后调用 `maybe_label_prose_figures_with_llm`，改为经 §0.3 的 `assist_json` 调用：
   - 给每个数字标出指标、期间、单位；
   - 同时找出代码没抽到的中文写法，比如"三成""翻倍"，作为新的数字加入核验清单；
   - LLM 不能删除代码抽出的数字，只能补充和标注。

3. **匹配（代码筛候选 + LLM 判断 + 代码复核）：**
   - **代码先筛出候选来源：** 按数值换算后在容差内相等，再加期间相符或未注明期间，从证据台账、模型单元格、来源记录里找出候选，最多 5 条。**数值比较一律换算后比较，不再用字符串。**
   - **LLM 判断每一条候选：** 输入是数字所在的句子和候选来源的片段，输出：`{verdict: supported | contradicted | unrelated, quote: "原文中支撑或矛盾的那一句", reason}`。
   - **代码复核 LLM 的结论：**
     - `quote` 必须逐字出现在来源原文里，否则这一条判定作废，按 `unrelated` 处理；
     - 判定为 `supported` 时，`quote` 里必须包含换算后相等的数值。
   - 有脚注、并且指向明确证据的数字，仍然走原来的确定性匹配。LLM 只用在没有脚注、或确定性匹配失败的数字上。

4. **结论分四类，处理方式不同：**

   | 结论 | 含义 | 发布时怎么处理 |
   |---|---|---|
   | 已核实 | 有来源支撑 | 通过 |
   | 有矛盾 | 有来源，但来源说的不是这个数 | **阻止发布**，告诉分析师哪里不一致 |
   | 无来源 | 找不到任何来源 | 分析师要么补来源，要么标成 `[估计]` 或 `[假设]` 并写明推导，否则**阻止发布** |
   | 未能判断 | LLM 失败或拿不准 | **不阻止**，在 PM 的审批卡上逐条列出，由 PM 决定 |

   草稿阶段（`check_draft`）对这四类都只给反馈，**一律不阻止**。

**验证方式：** 用审查报告里的反例构造一份测试草稿：
- DAP 512 百万（应判为有矛盾或无来源）；
- 表头写"广告收入（亿美元）"、单元格写 512 的表格（应判为已核实）；
- "市场份额约三成"（应被抽出来并要求补来源）；
- 正文里的 accession 号（不应被当作数字）；
- 正确带脚注的"+21%"（应判为已核实）。

**验收标准：**
- 以上五种情况的结果都正确；
- 拿一份真实的、正确的完整研究报告跑核验，误判为"有矛盾"或"无来源"的不超过 2 条，结果附在 PR 里；
- 把这几个反例写成测试，锁住结果。

**工时：** 2.5 天。

## 6. G5 broker 付费语义与 Antigravity

### G5.1 broker 的"不重复付费"（R1 问题 1、2、4、5）

**问题：** 防止重复付费的记录只存在进程内存里，网关一重启，同一个调用 ID 重试就会再付一次钱；客户端一断开就中止上游生成，重试时又要付一次钱。

**做法**（只做最小可用的版本，不按 P0.3 的完整设计逐条实现）：
1. **发送之前，** 往磁盘上的日志追加一条"进行中"记录；**完成时，** 把响应写入磁盘（文件权限 0600，保留 24 小时）。
2. **收到同一个调用 ID 时：**
   - 已完成：返回保存的结果；
   - 进行中、或进程重启后留下的进行中：返回 409"状态不确定"，不重发；
   - 失败且没有输出：允许重发。
3. **客户端断开时，** 不中止上游，把这次调用跑完并记录下来。只有超时和明确的取消才中止。
4. **日志按时间清理，** 只清理已完成的；内存缓存改为有上限、带过期时间。
5. **`/health` 的字段和管理端对齐**（R1-4）。
6. **B8：** 在 `dalton_meta` 里回显实际生效的推理档位，冒烟测试改读这个字段（P0F.6 的结论）。

**不做：**
- broker 层的显式回退（R1-6）。在决定记录里写明"broker 不提供回退"；需要回退时用 LangAlpha 自带的机制。
- 排队（R1-9）。保持超过并发上限时直接返回 429。

**验证方式：** 发一个长调用，中途重启网关，用同一个 ID 重试，返回 409，没有第二次计费；中途断开客户端，用同一个 ID 重试，拿到完整的结果。
