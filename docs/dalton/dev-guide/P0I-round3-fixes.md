## 0. 这一轮做什么、不做什么

**做：**
1. **堵住发布核验的错放**（第 1 节，本轮的核心）。上一轮堵的是误伤，这一轮堵的是错放：错放是正式成果里出现未经核实的数字，比误伤危险得多。

3. 修复审查列出的高危和中危：启动校验被吞掉、日志清理没有接线、前端红灯、多 worker 状态（第 3–6 节）。

**不做：**
- 新功能。
- **第三轮确认没问题的部分不要重构**，包括：
  - H3 的预检、认领、超时、议程探针、总监五条件；
  - 锚定的主链路：`quote` 逐字核对、`quote_number_raw` 核对、引文抽数比较；
  - 守门测试；
  - 冻结的词表。

  只做本文点名的修改，避免把已经审过的代码重新变成未审代码。

### 1.2 无脚注数字的"已核实"只能来自 D 环节（决定 L34）

| 路径 | 现在 | 改为 |
|---|---|---|
| Order 0–3：脚注指向事实台账、证据、模型单元格、来源记录 | 确定性匹配，可判"已核实"或"有矛盾" | **保持不变。** 但"有矛盾"只限于指标和期间都对得上、**数值换算后确实不同**；期间不一致、量纲不一致改判"无来源"，原因写明"脚注指向的证据期间（或量纲）与正文不一致"（L36） |
| Order 0b：无脚注时按指标、期间、数值查事实台账 | 直接判"已核实" | **只产生候选**，交给 D 环节 |
| Order 4：无脚注时自动搜索证据、一致预期、模型单元格、来源记录 | 直接判"已核实"；矛盾只进候选 | **只产生候选**，交给 D 环节 |
| Order 5：由其他数字推算出的比率、利润率、倍数 | 由已匹配的数字推算 | 保留，但**只能用 Order 0–3 或 D 环节核实过的数字推算**，不能用自动搜索的结果。在审批卡上标为"已核实（推算）" |
| SF-CN 特例（`a725c47f` 夹带的改动）：口语数字逐字出现在来源正文里时，用草稿自己的数值合成一个来源数字 | 等于拿草稿核验草稿 | **删掉。** 口语数字按 B 环节给出的数值（比如"两成"记为 20%）进入 D 环节，锚定方式和其他数字相同 |

**这条改动会让 D 环节的调用量大增，** 第 1.6 节给出批处理和缓存的做法。

### 1.3 迁移进来的旧认知不能作为核实依据（决定 L34）

1. 在 `thesis.schema.json` 的 `evidence.source.type` 枚举里新增 `legacy_thesis`。
2. **迁移脚本：** 由旧 `thesis.md` 生成的证据条目，`source.type` 一律写成 `legacy_thesis`，原来的 `broker_report`、`internal_note` 等类型移到 `source.identity` 里保留。
3. **活库：** 对四家已迁移的公司（META、AMZN、GOOGL、MSFT）追加一个修正版本，把 `ref.path` 在 `sources/legacy/` 下的证据条目改为 `legacy_thesis`，版本原因写"迁移的旧认知不作为核实依据"。**追加版本，不原地修改。**
4. **核验时：** `legacy_thesis` 条目不进入 C 环节的匹配，也不能作为 D 环节锚定的来源。它可以作为候选展示给分析师，提示文案是"旧认知中的说法，尚未用原始来源核实"。
5. 分析师后续用原始来源（SEC 文件、电话会、券商报告原文）补充证据时，新条目可以用 `supersedes` 指向旧条目。

**为什么不是只改验收方法：** 自证不只发生在验收里。分析师在生产中改写旧认知写成报告，报告里的数字会被同一份旧认知"核实"。

### 1.4 B 环节：全量标注，LLM 的标注优先（决定 L35）

| 项 | 现在 | 改为 |
|---|---|---|
| 送标注的数字 | 前 10 个 | **全部**，每批 40 个，逐批调用 |
| 送标注的正文 | 前 3000 字 | 按 Markdown 的二级标题切节，**每节单独送**。一节超过 6000 字时按段落继续切，相邻两块重叠一段。每批只带这批数字所在的节，加上全文的标题目录 |
| 口语数字的补抽 | 只扫前 3000 字 | 每节都扫。补抽的数字必须逐字出现在草稿的那一行里（现有的锚定保留） |
| 指标、期间、类型 | LLM 的标注只在代码启发式留空时生效 | **LLM 的标注优先。** 代码的启发式只在这一批标注失败时作为兜底，并且这批数字记为"标注未完成" |
| 新类型"非核验对象" | 没有 | `kind` 新增 `incidental`：点赞数、浏览量、HTTP 状态码、文件和文档编号、版本号、序号、页码等。**带货币、百分比、bp、倍数单位的数字不能标为 `incidental`**（代码检查，违反的忽略这个标注）。被排除的数字不进入核验，但**在审批卡上单独列出**，PM 可以展开查看 |
| 失败时 | 唯一的一次调用失败，`labeling_incomplete=True` | 任何一批失败，`labeling_incomplete=True`，审批卡写明"第 N 批（第 X–Y 个数字）标注失败"。失败批次的数字用代码启发式兜底，**不能被排除为非核验对象** |
| 输出 | 无覆盖统计 | 审计结果新增 `labeling`：`{total, labeled, batches, failed_batches, incidental_excluded, llm_period_overrides}`。**审批卡和证据里都要能看到"已标注 514/514"这样的数字** |

**期间解析的确定性修正**（属于格式识别，P0G 允许）：
- `normalize_period` 支持 `26Q4`、`Q4 26`、`Q4'26`、`FY26`、`2026Q4` 这些写法，"26Q4"里的 26 不再被抽成数字；
- 找到并修复"+33%"被标为 `3Q40` 的原因，补测试；
- "11 月""2026 年 11 月"这类中文月份进掩码表，和斜杠日期同类。

**不新增**用来识别点赞数、状态码、版本号的正则，这些交给 LLM 标注。

### 1.5 锚定补两项确定性检查，并修正四个分支（决定 L36）

**补两项检查。** 两项都是数值和格式检查，不是语义规则：

1. **量纲一致：** 百分比只和百分比比较，或者和明确写成小数的比率比较（现有的 0.21 对 21% 换算保留）。每股金额、货币金额、倍数、纯数字，各自只和同量纲的数字比较。`values_within_tolerance` 里百分比分支的 0.05 绝对容差，不能让"19.11 美元/股"等于"19.1%"。
2. **期间一致：** 用 `normalize_period` 解析引文里的期间。如果引文里有明确的期间、而且和草稿数字的期间都不相同，supported 不成立，判"未能判断"，原因写"引文期间与正文不一致"。引文里没有期间时不做这项检查。

**指标和主题仍由 LLM 判断，** 代码判断不了。但要让 PM 看得见：
- `JUDGE_SCHEMA` 新增必填的 `quote_metric_raw`，即引文里指明这个指标的原词。代码核对它逐字出现在 `quote` 里，否则判"未能判断"。
- 审批卡上，D 环节核实的数字单独成组，**每一条并排显示"草稿原句"和"来源引文"**。"资本开支余量 400 亿"对"最高 400 亿美元的 ATM"，PM 扫一眼就能发现。

**修正四个分支：**

| # | 位置 | 现在 | 改为 |
|---|---|---|---|
| 1 | `audit.py:300-305` | supported 但 `quote` 不在来源原文里，判"无来源" | **"未能判断"**（P0H §1.4）。同时改掉把错误行为锁成契约的测试 `test_publish_numbers.py:484-494` |
| 2 | `audit.py:313-330` | 用 LLM 自报的 `source_value`、`source_unit` 判"有矛盾"（单位不符） | **删掉。** 从 `JUDGE_SCHEMA` 里删掉 `source_value`、`source_unit` 两个字段（`audit.py:60-61`），兑现上一轮开发报告的说法 |
| 3 | `audit.py:332-335` | 同上，用自报数值判"有矛盾"（超出容差） | **删掉**，同上 |
| 4 | `audit.py:359-364` | LLM 判 supported、引文数字和草稿恰好差 10 的整数次方倍时，代码改判"有矛盾" | **"未能判断"**。需要判"有矛盾"时，由 LLM 判 contradicted、代码只做锚定 |

**修完之后，能产生"有矛盾"的分支只剩两类：** Order 0–3 的脚注数值确实不同；D 环节 LLM 判 contradicted 并且锚定成功。在测试里枚举所有能产生 `contradicted` 的代码位置，锁住这一点（可以用一个扫描 `contradicted`、`source_conflict`、`unit_mismatch`、`period_mismatch` 赋值点的测试）。

### 1.6 D 环节的批处理、时限和候选

所有无脚注的数字都要经过 D 环节，一份 500 个数字的报告会有几百个待判数字。

| 项 | 做法 |
|---|---|
| 批处理 | 一次调用判多个数字：同一节的数字每 10 个一批，每个数字附上自己的候选来源 |
| 缓存 | 按节分批，**修改一节只会让这一节的批次失效**，其他节命中 `dalton_complete` 的缓存。缓存键包含模型名（现状如此，确认不被破坏） |
| 候选数量 | 证据总数不超过 30 条时，全部作为候选；超过时按"数值相等（换算后）→ 期间相同 → 指标别名粗匹配"的顺序排序，取前 8 条。**修复 `retrieve_candidate_sources` 的截断问题**（`fallback_pool[:limit]`）：第三轮实测，正确的证据明明在，却因为排序靠后被截掉（GOOGL 的 2,425 亿现金、5,140 亿积压） |
| 并发与时限 | 并发保持 4。总时限从固定的 120 秒改为 `max(120, 待判数字数 × 2)` 秒，上限 900 秒。超时未判的数字判"未能判断"，审批卡写明"核验步超时" |
| 任务异常 | `audit.py:696-697` 的 `_ = d_task.exception()` 改为打 warning，这个数字判"未能判断" |
| "无来源"要附候选 | D 环节结束时，把这个数字的前 5 条候选写进最终条目（现在只进了 LLM 的输入，审批卡上是空的） |
| `legacy_thesis` | 不进候选的锚定来源，只作为"旧认知中的说法"附在条目上 |

**花费估算（PR 里给出实测值）：** `assist` 角色默认是订阅模型，现金成本为 0，需要关注的是订阅的速率限制。按 500 个数字估算：标注约 13 次、判断约 50 次。PR 里附一次真实报告的调用次数、耗时和名义成本。

### 1.8 验证与验收（G3 族）

**先建测试集，再改代码。** 测试集是这一族的验收依据，**要提交进仓库**，审查人才能重跑。

1. **草稿：两份真实报告，来自两家不同的公司。** 用 GOOGL 底稿（`var/dalton/migration/raw/GOOGL.json` 的 `raw_thesis_md`），再加一份 PS 试跑的产出或另一家公司的底稿。
2. **证据：从原始来源独立整理。** 用 SEC 的 10-Q、10-K、8-K 原文和电话会记录，每条证据的 `source.ref` 指向原始文件（accession 号或 URL）。**不能用迁移生成的 `thesis.json`。** 公开来源的原文片段和整理好的证据放进 `tests/fixtures/dalton/g3/`；内部资料不进仓库，只放来源 ID。
3. **金标准：** 每份报告挑 2–3 节，合计约 150 个数字，逐个标注三项：是不是财务数字；在证据集里有没有真实的来源，有的话是哪一条；期间是什么。**开发者起草，审查人或 PM 复核所有标为"有来源"的条目。** 金标准也提交进仓库。
4. **反例：**
   - 第三轮的 10 个错放全部写成测试：点赞数、HTTP 500、文件名编号、月份、"26Q4"、"Sonnet 5.5"、三个期间错标；
   - 两个锚定盲区："400 亿 ATM 对资本开支余量"，"19.11 美元/股对 19.1%"；
   - S1：supported 加编造的引文，判"未能判断"；
   - 迁移的旧认知不能核实数字；
   - 修改一节之后重跑，其他节命中缓存。

   LLM 相关的测试用带 `spec=` 的替身固定返回。
5. **真实运行（真实 LLM，新建测试用户，保证不命中旧缓存）：**
   - 两份报告各完整跑一次 `publish_report` 的核验；
   - 交叉对照：GOOGL 草稿配 META 的证据；
   - 注入实测：沿用第三轮的场景。

**验收标准：**

## 2. 真实运行证据的规范和工具（I2，决定 L37）

第三轮的证据问题集中在四类：
- **证据的生成脚本不在仓库里，** 换一个人没法复现；
- **在内部函数层面验证，却写成了真实运行：** G1 直接调用准入函数，G4 直接调用预检、直接写状态表；
- **模拟和缓存没有声明：** G7 是模拟的延迟；G3 的口语数字场景是缓存回放；
- **证据里的数字和调用日志对不上：** G1 的 $1.05，G2 的 $0.00051。

### 2.1 规范

1. **脚本入库。** 每一族的证据由 `scripts/dalton/realrun/g<N>_<短名>.py` 生成，**通过真实后端的 HTTP 接口操作**，不导入 `src/dalton` 的内部函数。确实需要内部调用的，在证据里声明（见第 4 条）。
2. **证据的固定头部。** 每份证据 JSON 都以下面的字段开头：

   ```json
   {
     "evidence_version": 1,
     "git_sha": "<运行时的 HEAD>",
     "script": "scripts/dalton/realrun/g1_budget.py --cap-usd 0.02 ...",
     "started_at": "...", "ended_at": "...",
     "backend": "http://127.0.0.1:8000", "test_user_id": "...",
     "synthetic": [],
     "journal": { "rows": [...], "totals": {...} }
   }
   ```

3. **调用日志对账。** `journal` 由 `scripts/dalton/realrun/journal_dump.py --user <id> --since <t0> --until <t1>` 生成，内容是这个时间窗口里这个测试用户的每一条 `dalton_llm_journal` 记录，字段包括：调用 ID、用途、模型、状态、是否缓存或回放、用量、现金和名义花费、时间。**不含请求和响应正文。** 证据和报告里的调用次数与花费，**一律从这些记录汇总得出，不能手写。**
4. **声明非真实成分。** 注入的状态、模拟的延迟、测试替身、预先写入的数据，逐项写进 `synthetic`，并写明经过的入口。**允许的注入**只有下面四类，必须经过系统本来就用的入口：
   - 通过设置接口修改额度；
   - 通过知识层接口或工具修改议程；
   - 从 `dalton_watch_state` 的"已看到"集合里去掉某一份公告；
   - 已入库的、默认关闭的测试钩子，比如第 7 节 G7 的延迟钩子。

   **不允许：** 直接往信号表、调用日志、预算表写行；直接调用 `preflight_check`、`enforce_local_admission` 这类内部函数。场景里出现不允许的成分，这个场景按 🟦 算。
5. **缓存回放不能代替真实调用。** 证据里每次 LLM 调用都要带 `replayed` 标记。需要证明"真实 LLM 做了某事"的场景，**必须有一条 `replayed=false`、用量大于 0 的记录。** 用新建的测试用户、或在输入里带上本次运行的编号，确保不命中旧缓存。
6. **摘要入库。** 原始 JSON 仍然放在 `var/dalton/`（被 `.gitignore` 忽略）。每一族在 `docs/dalton/dev-guide/trial-runs/realrun-<日期>/G<N>.md` 写一份摘要，内容包括：运行命令、关键字段、调用日志汇总表、原始 JSON 的 sha256，不含凭据。**PROGRESS.md 的证据路径指向这份摘要。**

### 2.2 工具

| 工具 | 作用 |
|---|---|
| `scripts/dalton/realrun/journal_dump.py` | 按用户和时间窗口导出调用日志记录（第 2.1 节第 3 条） |
| `scripts/dalton/realrun/_common.py` | 生成证据头部、计算 sha256、写摘要模板；封装登录和接口调用 |
| `scripts/dalton/check_report_claims.py` | 扫描开发报告和 PROGRESS.md：反引号里的标识符（函数名、类名、正则名、文件路径）在仓库里能不能找到；`var/` 下的证据路径存不存在。**只报告，不阻止**，结果附在 PR 里 |

**验收标准：** 三个工具入库，并且在第 7 节的证据重做中实际使用。用 `check_report_claims.py` 扫描 P0H 的开发报告，能报出第三轮审查发现的那些不存在的名字（作为对这个工具的验证）。

**工时：** 1 天。
