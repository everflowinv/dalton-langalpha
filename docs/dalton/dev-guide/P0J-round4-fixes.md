### 1.2 身份：证据环境用真实的按用户身份（决定 L40）

1. **证据环境的 `.env` 设置 `INTERNAL_SERVICE_TOKEN`。** 脚本的每个请求都带 `X-Service-Token` 和 `X-User-Id`。这是上游本来就有的服务间认证路径（`_service_token_user_id`），不需要改代码。令牌只放在 `.env`；证据里只记 `identity_mode: "service_token"`，**不记令牌的值。**
2. **测试用户的 PM 权限通过配置提供，不进代码**（L39）：
   - `src/dalton/settings.py` 里有两份 `pm_user_ids`（第 58 行和第 123 行），**合并为一份；**
   - 默认值改为 `[LOCAL_DEV_USER_ID]`（从 `src/config/env.py` 读取，跟随 `AUTH_USER_ID`），**删掉 `"local_dev_user"` 和 `"default"`；**
   - 增加环境变量 `DALTON_PM_USER_IDS`（逗号分隔），覆盖默认值；
   - 证据头部记录 PM 名单的来源（`pm_user_ids_source: "env"`），不记名单本身。
3. **需要证明"按用户"的场景，至少用两个测试用户：**
   - G1：用户 A 花完额度被拒，用户 B 同时不受影响；
   - G2：PM 用户能调用 PM 接口，非 PM 用户得到 403；
   - G3、G4：工作区属于用户 A，用户 B 看不到。

   **固定的测试用户 ID**（`.env` 已按此配置，第 8.1 节第 7 条）：

   | 用户 | ID | 用途 |
   |---|---|---|
   | PM 测试用户 | `realrun-pm-a` | 在 `DALTON_PM_USER_IDS` 里。G2、G3、G4 里需要 PM 权限的操作 |
   | 非 PM 测试用户 | `realrun-user-b` | 不在 PM 名单里。G2 的 403、G3 和 G4 的隔离 |
   | G1 的预算用户 | `realrun-g1-<运行时间>-a`、`realrun-g1-<运行时间>-b` | 每次运行新建，因为额度按天计算，复用会被当天已有的花费干扰 |

   每次运行的隔离靠新建的工作区和对话，不靠新建 PM 用户。
4. **身份自检：** 每个脚本结束时，用 `journal_dump.py` 查这个时间窗口内 `dalton_llm_journal` 和 `conversation_usages` 的全部记录，**断言每一条的用户都是本次声明的测试用户之一，没有一条记在 `local-dev-user` 名下。** 断言失败，这份证据标为无效。

### 1.3 版本：证据只能在干净的、已合并的提交上生成（决定 L41）

1. **后端报告自己的版本。** 在 Dalton 已有的健康检查接口（`GET /api/v1/dalton/openclaw/health` 或新加的 `GET /api/v1/dalton/health`，二选一，选改动小的）里，返回进程启动时记录的 `git_sha` 和 `git_dirty`，以及当前请求者的 `user_id`。最后一项同时用于第 1.2 节的身份确认。
2. **证据头部新增字段：**

   ```json
   {
     "evidence_version": 2,
     "git_sha": "...", "git_dirty": false,
     "backend_git_sha": "...", "backend_git_dirty": false,
     "script_sha256": "...",
     "identity_mode": "service_token", "pm_user_ids_source": "env",
     "deployment": "docker" | "host",
     "valid": true, "invalid_reasons": []
   }
   ```

3. **脚本拒绝在下面这些情况下运行**（退出码非 0，不生成证据）：
   - 工作区不干净；
   - 后端的 `git_sha` 和脚本所在的 HEAD 不一致，或者后端的工作区不干净；
   - 当前 HEAD 不在 `origin/dalton/main` 上，也就是没有合并。

   **不提供跳过这些检查的参数。** 开发调试时可以直接跑脚本，但不加 `--record`，不生成证据文件。
4. **证据族的 PR 只包含文档**（摘要和开发报告）。跑证据时发现代码问题：**停下来，在对应族的分支上修，审查合并之后，在新的提交上重跑所有受影响的证据。**

### 1.4 证据环境检查

### 1.5 注入声明：按入口校验（L37 的修订）

**正常的用户操作不算注入：** 建测试用户、建工作区、写草稿、发起对话、触发自动任务。**预先写入的数据和非真实的成分算注入，** 必须声明。允许的类别改为下面 6 类，`validate_synthetic_declarations` 同时校验类别和 `entry_point` 是否匹配：

| 类别 | 允许的入口 | 用途举例 |
|---|---|---|
| `settings_api_budget` | `PUT /api/v1/dalton/budget` | 设置测试用户的额度 |
| `knowledge_api_agenda` | 知识层的议程接口或工具 | 写一条到期的验证 |
| `knowledge_api_import_fixture` | 知识层的导入接口，导入的文件必须在 `tests/fixtures/` 里 | G3 导入独立整理的证据 |
| `watch_state_unsee_filing` | 只改 `dalton_watch_state` 里的"已看到"集合 | G4 让一份真实公告重新出现 |
| `committed_test_hook` | 已入库、默认关闭、只在测试模式下生效的钩子，必须列在一张登记表里（`_common.py` 里的常量），并写明代码位置 | G7 的桥接延迟 |
| `committed_fixture_input` | 已入库的输入文件，作为确定性脚本的输入 | G6 的财务报表科目 |

**删掉 `registered_test_hook`。** 下面这些**一律不允许，出现即判证据无效**：
- 直接写凭据表、信号表、调用日志、预算表；
- 在脚本里导入并调用 `src/` 的内部函数；
- 用 mock 替换生产代码的行为。

`check_env.py` 可以静态扫描 `scripts/dalton/realrun/g*.py`，检查有没有 `from src` 导入和直接的 `INSERT INTO`，有就报错。

### 1.6 摘要和报告里的数字由脚本生成（决定 L42）

1. **摘要：** `G<N>.md` 全部由 `_common.py` 从证据 JSON 渲染生成，不手工编辑。确实需要人工补充的说明，写在 JSON 的 `notes` 字段里，一起渲染。

### 2.3 非核验对象：只有九类，由 LLM 判断（决定 L43）

1. **九类：**
   1. 点赞数、转发数等社交互动计数；
   2. 浏览量；
   3. HTTP 状态码；
   4. 文件、文档、邮件和 URL 里的编号；
   5. 软件和模型的版本号、硬件型号（如 Sonnet 5.5、B200）；
   6. 列表序号、页码；
   7. 用户名里的数字（如 @kashyap286）；
   8. 机构、产品、节目名称里的数字（如 a16z、Law360、财富 100 强）；
   9. 期间、日期和时间窗口表达里的数字（如"过去 12 个月"、"近 30 天"、1Q27 里的 27）。

   **第 8、9 类是 J2a 复核金标准时补上的。** 原来的七类没有这两类，按字面，这些数字都得当成核验对象，发布时会被大量误拦。
2. **不是非核验对象：** 研究报告里的**事实陈述**，不论单位是什么，都要进入核验。比如装机容量、合同期限、样本量、覆盖半径、调查家数、量子比特数。B 环节的指令里，把九类和这几个反例都写进去。
3. **代码守卫：** 第 2.2 节保留的那几项。失败批次的数字一律回落为普通数字，不能被排除（修 R2-d）。
4. **审批卡：** 被排除的数字逐条显示原句和 LLM 给出的类别（属于九类中的哪一类），PM 可以展开查看。顺带把 `failed_batch_details` 渲染出来："第 N 批（第 X–Y 个数字）标注失败"（R4-publish P10）。

**这样做的代价：** 事实陈述没有脚注时会被判"无来源"，发布时会被拦下，要求分析师补来源。这是 L28 本来就有的要求，不是新增的阻塞，草稿阶段仍然不卡。

## 4. 流程与报告纪律（J4）

### 4.1 合并之前必须有审查

L32 要求一族一个 PR，目的是在合并之前审查。P0I 的 8 个 PR 都是零审查、自己合并的。

**问题：** 开发方和 owner 用的是同一个 GitHub 账号（`everflowinv`），GitHub 不允许批准自己的 PR。

**做法（owner 决定，第 8.1 节）：**
- **推荐：** 开一个单独的审查账号，给 `dalton/main` 设分支保护：至少一个批准才能合并，管理员也不能绕过。
- **过渡办法：** lead 在 PR 里留下固定格式的审查评论（`审查：通过 / 不通过` 加原则自查表的核对结果），**由 lead 合并，开发方不合并自己的 PR。**

### 4.2 PR 描述和 diff 对账

PR #7 的描述有两处和 diff 不符："回退到 CLI 网关"、"修了 open_questions 的计数"。从这一轮起：
- PR 描述里的每一条说法都写明对应的文件和行号（第 0.2 节自查表第 6 条）。
- 把 PR 描述保存成文件，用 `check_report_claims.py` 扫一遍，输出附在 PR 里。它查不出语义上的不实，但能查出不存在的名字。
- 审查人逐条对照 diff。

### 4.3 不夹带

- 一族的分支只包含这一族的改动（第 0.2 节自查表第 7 条）。
- 证据族的 PR 只包含文档（第 1.3 节第 4 条）。

### 4.4 owner 邮箱的 git 历史

**决定：不重写历史。**
- 这是私有仓库，邮箱是 owner 自己的。
- 重写 `dalton/main` 需要强制推送，所有分支和 PR 的引用都会失效；GitHub 上已合并 PR 的提交引用不会因此消失，重写也清不干净。
