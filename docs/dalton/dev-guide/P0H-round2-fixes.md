## 1. 发布核验的职责重新划分（本轮的核心）

### 1.1 问题出在哪

第二轮审查的反旧 Dalton 审计（`R2-anti-pattern-audit`）发现，发布核验的确定性规则还在长：
- 中文数字正则约 95 行，"三成""八折""五分之一"之类，每多一种写法就要再加；
- 指标别名表又扩了 4 组；
- 增速和利润率的词表；
- **一行里出现"一致预期"，整行的数字都被判为 consensus，直接判"有矛盾"，阻止发布，并且跳过 LLM 复核**（`numbers.py:931`、`match.py:829-887`）。

在 META 的真实底稿上，835 个数字里有 331 个被误判为"有矛盾"或"无来源"，P0G 的验收线是不超过 2 个。主要原因有三个：
- 整行标签误判：178 个；
- 数值碰巧相同被判为"有矛盾"：111 个；
- 斜杠日期、编号被当作数字：约 42 个。

同时，P0G 要求接上的 LLM 标注器 `maybe_label_prose_figures_with_llm` 又一次没有接上，这是第一轮 R4-7 的复发。

**根源是：代码自己能判出"有矛盾"。** 只要代码可以独立地把一个数字判为矛盾，每发现一次误伤，就得补一条例外规则。这正是旧 Dalton 的循环。

### 1.2 新的分工（决定 L28）

| 环节 | 谁来做 | 能产生什么结论 |
|---|---|---|
| A. 抽取 | 代码 | 候选数字。日期、时间、编号等用掩码排除 |
| B. 标注 | **LLM，每份报告必经** | 每个数字的指标、期间、类型（实际值、估计、一致预期、公司指引），以及代码漏抽的口语数字 |
| C. 脚注匹配 | 代码 | **已核实**：脚注指向的证据数值换算后相等。**有矛盾**：脚注指向的证据，其数值换算后确实不同 |
| D. 无脚注、或脚注匹配失败的数字 | **LLM 判断 + 代码锚定** | 已核实 / 有矛盾 / 无来源；锚定失败时为"未能判断" |

**规则：**
1. **除 C 环节的脚注数值不符之外，代码不能独立判出"有矛盾"。** "有矛盾"必须来自 LLM，而且要被锚定到原文中真实存在的数字（见 1.4）。
2. **数值碰巧相同、但指标或期间对不上，** 判为"无来源"，并附上候选来源供分析师参考，**不判为"有矛盾"**。
3. **B 环节的标注失败时**（LLM 超时、额度不足），整份报告在审批卡顶部显示"标注未完成，口语数字和指标可能未核验"，交给 PM 决定。**不退回到规则。**
4. **代码里的语义规则只能用于候选的排序和粗筛，不能决定结论。**

### 1.4 LLM 判断的锚定：修复严重问题

**严重问题（`audit.py:217-244`）：** 复核做了一半。
- 已经做了：引用的原文逐字存在、单位不冲突。
- 第 220 行把"引文里的数值和草稿是否一致"的比较结果丢掉了。
- 第 228 行的第二个要件，比的是 LLM 自己报告的 `source_value`。

所以只要 LLM 返回一段真实存在的引文，再加一个和草稿一致的 `source_value`，编造的数字就会被判为"已核实"。不需要任何提示词注入，LLM 引错了一个同单位的数字，也会静默通过。

**修法：锚定只认原文里真实存在的数字。**

| LLM 的结论 | 代码复核的要件（全部满足才采信） | 不满足时 |
|---|---|---|
| supported（已核实） | ① `quote` 逐字出现在来源原文中；② 从 `quote` 里抽出的数字中，**至少有一个**换算后和草稿的数值相等；③ 如果 LLM 报告了 `source_value`，它必须等于第 ② 条找到的那个数字 | 判为"未能判断" |
| contradicted（有矛盾） | ① `quote` 逐字出现在来源原文中；② 从 `quote` 里抽出的数字中，有一个是 LLM 指明的对应数值，并且换算后和草稿的数值确实不同 | 判为"无来源"（附候选），**不判为有矛盾** |
| exempt（豁免核验） | LLM 必须给出草稿里的豁免标记原文，比如 `[估计]` 或 `[假设]` 加推导说明，**代码逐字核对它确实出现在这个数字所在的句子里** | 拒绝豁免，按"无来源"处理 |
| unrelated（无关） | — | 换下一条候选；所有候选都无关时，判为"无来源" |

**一句话：** LLM 告诉我们"哪句原文、哪个数字"，代码去原文里亲自找到这个数字、亲自比较；LLM 自己报的数值一概不作为依据。

## 9. 开发流程的硬性要求（决定 L32、L33）

第二轮暴露了三类流程问题，从这一轮起作为硬性要求：

1. **一族一个分支、一个 PR。** 上一轮把 8 个族合成了一个提交、141 个文件，审查和回滚都很困难。本轮按第 8 节的 H1–H7 分别开分支，命名为 `fix/P0H.<族>-<短名>`。
2. **PR 描述必须附真实运行的证据，** 按每一族的"验证方式"逐条列出。没有证据的 PR 只能标为 🟦，不能合入后在 PROGRESS.md 里写成"已验证"。
3. **测试替身必须声明参数**（`unittest.mock` 用 `spec=` 或 `autospec=True`）。**禁止 `mock(**kwargs)` 这种能吸收任意参数的写法。** 这一轮有三次"必败代码却绿灯通过"：分诊的错误签名、`provider_status` 的路由测试，以及第一轮那个锁定错误行为的预算测试。
4. **守门测试要实际调用。** G2 的守门测试扩展为：每个接口除了检查引用能解析，还要实际调用一次它背后的服务函数（数据库和外部调用用带 `spec=` 的替身），这样能抓住"导入了不存在的函数"这类问题。
