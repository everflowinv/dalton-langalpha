## 常规审查（并发/事务边界）

- **多 worker 状态以 Postgres 为准**：预检全程无模块级可变状态；信号生命周期（pending/woken/resolved/expired）只由 `dalton_signals` 行上的时间戳列表达，`claim_signals_woken`/`resolve_signals`/`expire_old_signals` 都是带守卫条件的单语句 UPDATE——多进程并发下由行锁仲裁，符合项目多 worker 原则。`settle_execution` 把执行状态与 automations 侧效果放同一事务（`conn.transaction()`，先 `FOR NO KEY UPDATE` 锁 automations 再 `FOR UPDATE` 锁执行行，顺序与级联删除一致）。
- **`upsert_watch_state` 整份 JSON 覆盖**：两个并发预检各自带着 state 副本最后写库，后写覆盖先写（丢水位更新）。影响有界：水位回退最多让探针重发同一 `signal_key`，信号表 `is_unwoken=False` 会挡住二次唤醒；watch（6-20 点每 30 分钟）与 delta（21:30）cron 基本错开。记为低（见问题表 #3 的说明段，未单列）。
