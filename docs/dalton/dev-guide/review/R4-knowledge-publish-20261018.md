# R4 知识层与发布治理 审查结果
审查人：ZCode 审查智能体  日期：2026-10-18  代码版本：20232e5f（源码与 7670a03f 相同）

## 结论
知识层的版本化、三条硬不变量、发布状态机（批一次执行一次）、不可变发布物、并发控制实现得很扎实，迁移和上游挂钩都符合约定。但**数字核验引擎存在一个严重漏洞**：对 provenance 正文的自动匹配只核对数字和期间、不核对指标关键词（设计 PK.9 明确要求两者），跨指标、跨量级的编造数字可以蒙混过发布闸门（已实测复现）。此外：审稿人的"不同家族"保证因作者模型永远取不到而失效；PM 审批卡前后端字段名对不上、卡片信息为空；表格单位写在表头（中文研报的标准写法）会被判 unit_mismatch 卡住发布；"有发布成果的工作区不能删除"完全没实现。**建议先修问题 1–5 再进入 P3 验收。**

测试：`uv run pytest tests/unit/dalton -q` 72 项全部通过；另用离线脚本直接调用 `extract_figures` / `audit_draft` 构造草稿文本实测（不经过 LLM、不碰数据库）。

## 已确认没问题的关键点
- **三条硬规则（工具路径）**：I1 证据台账 append-only（旧元素原位保留，删/改任一条即 `append_only_violation` 硬错误，实测删 evidence[0] 被拒且不落库）；I2 `thesis.official`/`house_view.official_version` 仅 `source='publish'` 可写（tool/import/server/direct_edit 全被拒，`source='publish'` 只有 run_publish 一处设置）；I3 目标价必须 `kind=model_cell` + path + `Sheet!Cell` 且登记于 models.json。发布侧另有 `_RequiresModelCellOnly`：草稿里的目标价/IRR/三情景收益只能匹配模型单元格。
- **直接修改路径（Bash 与文件面板同一条检测链）**：两者都落沙箱文件 → 轮末 `backup_changed_projects` 镜像进 `workspace_files` → `detect_direct_edits` 对比 `content_hash`（上游 sha256(bytes) 与 canonical_json 的 sha 同源）与版本行 sha → 记 `direct_edit` 版本，不合 schema 时 `schema_valid=false` + 中文警告 + agent.md 托管块提示；不拦截（ProtectedPathMiddleware 不覆盖 data/、PUT files/write 无 dalton 钩子）、不回写用户改的 JSON、渲染回落 `latest_valid_version`。md 被直接改时原文存 `history/<doc>/…-edited.md` 后重渲染。
- **数据库不可变**：d003/d005 迁移与设计一致——`dalton_verdicts`、`dalton_publications`、`dalton_publication_files` 挂 `dalton_forbid_mutation` 触发器拒 UPDATE/DELETE；版本表触发器只允许回填 `files_written_at` 类字段外的内容变更拒绝；downgrade 干净。
- **并发**：`insert_version` 在 `pg_advisory_xact_lock` + `UNIQUE(workspace_id,doc_key,version_no)` 内读最新、CAS（tool/import）、顺序追加（direct_edit/publish/server），两进程并发不丢版本、后到者收 `version_conflict`；VD id 分配同样在锁内。
- **批一次执行一次**：`get_or_create_request` 以 `UNIQUE(thread_id,tool_call_id)` 幂等（ON CONFLICT 只碰 updated_at）；`consume_approval` 是唯一执行令牌（单条 UPDATE … WHERE status='approved' AND bundle_sha256=%s）；`insert_publication` 按 publish_request_id 幂等；重放/重复提交/崩溃恢复（publishing 重入）都不会双发；审批后草稿被改 → bundle 不符 → superseded。
- **无人值守发布**：线程 origin ∈ {automation, agent} 时不发 interrupt，写 agenda `pm_handoffs{kind:publish_approval}`，停在 awaiting_pm 并返回 request_id——不会触发 settlement 的"HITL 即 FAILED"路径；PM 之后在交互线程以 `request_id` 续批，不重跑核验/审稿。
- **审稿权威性**：结论由服务端 `LLMService.complete`（无工具、结构化 ReviewVerdict、must_fix 强制 revise）产生并写入 `dalton_publish_requests.review`；`publish_report` 没有"已审稿"入参，作者无法伪造；模型不可用/调用失败/解析失败一律 `review_unavailable`（草稿可读、不能发布），不误判为 pass；审稿人不可用时还会在 agenda 里追加 data_access 待办。
- **published/ 不可变**：`_pick_non_colliding_path` 同 sha 幂等、异 sha 追加 -2/-3 后缀，绝不覆盖；文件字节永久存 `dalton_publication_files.content`（BYTEA，不受 blob GC 影响），可按 DB 内容+hash 手工恢复（设计如此；注意目前只能 psql 取，API 不返回字节）；被删改时 reconcile 只在日志与托管块警告。
- **抽取与误伤（正文）**：亿/万/百万/千亿/bn/b/mn/%/pp/bp/x/美元/港元 均正确抽取换算（512 亿美元 ↔ USD_mn 51200 实测匹配）；范围 "20–25%" 两端各自抽取并分别匹配指引上下限；表格 metric=行表头、period=列表头正确；日期（ISO/中文/短横线）、FY/季度 token、10-K/10-Q/8-K、E-/VD-/V-/Q- 等实体 id、"第 N 节/页/季度"结构计数、免责声明段、引用块、代码块、markdown 链接均正确排除；四舍五入容差（±0.5 末位、百分比 ±0.05pp、跨单位换算）实测合理（81.4%↔81 ✓、27.10↔27.104 ✓）；编造数字（599 亿）、无来源数字、Q2 数写成 Q3（period_mismatch 且给出中文候选说明）、增速写成利润率（指标不匹配）全部被抓出。
- **工程约定**：上游改动全部带 `DALTON-HOOK` 标注（agent.py 两处、ptc_run.py 一处、ToolApprovalCard.tsx 一处等）；dalton 目录无 `except: pass`；多 worker 状态全在 Postgres（进程内仅有 `reconciled_workspaces` 去重缓存，不影响正确性）；工具 docstring 符合直连工具一行 Returns 约定；只挂主智能体、子智能体不带知识/发布工具；`tests/unit/dalton` 72 项通过。

## 疑似问题（未能确认）
- **detect_direct_edits 的 sha 一致性未在真实栈上验证**：代码读下来 canonical_json 写入 → 备份 → `content_hash` 应一致，但"沙箱写入→备份镜像→DB 对比"的完整 roundtrip 需要起栈实测（尤其备份是否做换行/编码归一）。若不一致会出现每次更新后都多一条假 direct_edit 版本——上线前跑一次 PK.5 验证 1 即可确认。
- **FilePanel 编辑的检测延迟**：只在"下一次 turn 结束"触发，长期无 turn 的工作区直接修改不会被发现（设计已接受此延迟，列出备查）。
- **`_resolve_thread_origin` DB 异常时回退交互路径**：自动任务 run 里会误发 interrupt → 该 run 被 settlement 记 FAILED。仅 DB 故障边界情况出现。
- **dalton-reviewer.md 的固定 `model:` 初始值**依赖 `scripts/dalton/apply_role_models.py` 在主模型切换后改写（L16）；本次未运行该脚本验证它确实会更新此文件（尤其家族冲突时是否报错）。
