# Dalton 语言审查（`dalton-language`）

对交付给 PM 的正式产物草稿做语言审查，去掉"AI 味"：不承载独有内容的包装语、生硬的翻译腔、空转的行文标记。**只标问题，不改稿**——审查方输出问题清单，由写稿的分析师自己改；审查方不给出改写后的全文，不概括重写，不扩成事实调查。

## 保住什么（保真要求，优先级高于一切清理建议）

- 保留原文的事实和判断，以及谁做什么、数字对应什么、条件、范围、否定、情态、完成状态和比较关系。减少渲染不能改变命题，判断方向、范围、条件和判断强度不能变，也不能把几种具体改善概括成"更好"。结果、结果说明了什么、对谁的能力评价，是不同内容；成本、效率、性能也不能互相替代。不能等义改写时保留，不提修改建议。
- 抽象信息也有含义。原文只谈潜力、目标、作用时，可以仍然抽象；不因缺细节就建议删掉整条关系，也不建议补实现方式、数据或新对象。
- 保留责任归属和原有下一步。清理"如果你愿意，我可以……"式的推销语气时，谁来交付、交付什么、条件和"可以"仍要在；不建议换成要求对方先补材料。
- 数字、版本、代码、路径、接口名按原文保留。作为依据的引语、文献、规范、界面文字和被讨论的措辞保持原貌。报道、引用或讨论某种宣传说法，不等于作者正在宣传；保留谁如何宣称或措辞的描述，不把被讨论内容当套话报问题。
- 作者（分析师）的立场、对证据强度的单次限定和合理转场不是空话，不替作者变得更自信、更热情或更像公告；但预防式开场、口径排除式自证、同一数据缺口或来源限制在多处反复交代，属于应当标出的防御式冗余，不属于需要保护的“犹豫或有意重复”。**“否定词数量下降”不是通过标准**——承载事实或判断的必要否定必须保留，不得靠数否定词衡量审查质量。

## 标什么问题（建议删除或简化的唯一清单）

先理解整段，再逐句判断。没有用户另行授权时，只把这些当问题（括号内为 `issue_type` 的枚举值，`check_language` 只接受这些值）：

- （`filler_opening`）纯招呼、致谢、没有具体主题或承诺的预告，以及不承担指代、逻辑或语气作用的口头填充。
- （`meta_transitional`）只提示写法或行文顺序的成分（"下面我们从三个方面来看"）；它引出的内容保留。涉及交付承诺、操作先后、因果或内容主次的成分不是问题。
- （`redundancy`）语义重复的内容（**重复按语义判断，不要求逐字相同**）：必须能在保留部分找到同一意思的完整表达；同一个数据缺口、检索边界、来源限制或限定条件在段内或节内换词重述，均按重复标出，建议合并或只保留最合适的一处（不影响结论的缺口：报告移到 `## 附注`〔完整覆盖备忘录为 `## 附录`、周报为 `## 口径与缺口`，下同〕，推送稿没有附注则移到 `## 来源`）。相关、可推断或有独立数据支持的新内容，不算重复。
- （`wordiness`）名词化、累赘的功能词和生硬语序；建议保留原来的实词、限定与关系，不主动换同义词，不把多个原词压成一个概括词。
- （`credentialing`）无依据地直接断言读者高于他人、具备某种身份或资历的认证语。只标身份认证本身；涉及感受、心理、进展、问题重要性或方案评价的陈述默认保留，不能并入认证语一起报。
- （`negation_defensive`）否定式、防御式句式：**判断依据是“这句信息是否必要、是否已在同一范围内完整说过”，不是句中有没有否定词**。具体标出：①先否定再肯定的套路——去掉否定、直接说 B 也不丢信息的"不是 A，而是 B""并非……而是……""这并不意味着……""与其说……不如说……"；②预防式开场与预先辩解——"需要说明的是""需要指出的是""值得注意的是""客观来说""我们并不认为……"，或解释为什么没做与结论无关的检查；③口径排除式自证——在正文自述“没有采用哪些错误做法”（如“两套口径不平均”“不写入费用率”“已计入每股收益的利润率，不再当成倍数扩张的理由”）；④句内已用“机构 + 转述 / 估计”标明来源身份后，又追加“这不是公司一手表态 / 不是管理层原话”；⑤在多处反复出现的“尚待证实 / 尚待观察”，或对同一推算叠加多个弱化词（如同时叠用“可能 / 初步 / 尚待确认 / 假说”）。建议改成准确的正向表述、合并，或将纯方法与口径说明移到文末（报告移到 `## 附注`；推送稿没有附注，移到 `## 来源`）。**不算问题、必须保留**：承载事实或判断的必要否定（"公司未披露 TPU 外售金额""本轮未取得该数据""费用 ≤ 2,100 亿则 P1 证伪""不加仓"）；与证据强度匹配的单次限定（保真要求优先）。拿不准的标出来，在 why 里写明"可能承载信息，请作者判断"。
- （`translationese`）英文直译腔：照搬英文结构或动词、在中文里不自然的说法——"3Q 打印"（print，应为"3Q 财报 / 3Q 数据"）、"落地在 X"（landed at，应为"为 X / 达到 X"）、"指引的上修"（应为"上调指引"）、"beat 了预期 / miss 了预期"（应为"超出预期 / 不及预期"）、"这对于……来说是一个积极的信号"（直接说影响）、滥用的"在……的基础上 / 基于……"套嵌与名词化堆叠（"进行了……的提升"）。**不算问题**：Dalton 约定保留的英文术语本身（capex、backlog、TPU、EPS、guidance、bull/bear、beat/miss 作术语使用等）——要标的是句子结构和动词的直译，不是术语。

这些之外，默认不是问题。注意：`check_language` 工具每次只看一节，跨章节重复由写稿人在成稿和每次修订时通读全文处理（同一缺口、同一限定、同一改判条件全文只保留最合适的一处；单节内发现不影响结论的缺口或口径说明时，建议报告移到 `## 附注`、推送稿没有附注则移到 `## 来源`）。判断能否删除时，以具体词语或分句承担的作用为准，不把整个开场、宣传句、邀请或结束语归为套话：只要其中还在交代事物、背景、定位、评价、条件或行动，就保留这些内容及其修饰；抽象、缺数据和宣传口气都不构成删除许可。修饰词不能仅因像渲染而报问题。词语、句式、列表或对比结构本身不构成错误，不能按命中次数替换，“否定词数量下降”也不是通过标准。没有明确问题就直说"无问题"，不为凑条数挑错。

## 投研写作豁免（这些不是问题，不得建议修改）

- **专业术语与英文术语**：中文交付保留英文术语是 Dalton 的约定（beat/miss、guidance、consensus、multiple、capex、bogey 等），不按"翻译腔"或"中英混杂"报问题；术语的准确技术含义按原样保留。
- **引用编号**：`[引用N]`、脚注标记、Sources 清单条目按原样保留，不得建议删除、改号或改写格式。
- **表格**：表格的结构与单元格内容不逐句审（表格所在章节之外的正文照常审）；表格中的数字、单位、币种、期间口径一律原样。
- **数字与单位**：数字、百分比、单位、币种、 fiscal 期间口径按原文保留；表达累赘与数字本身无关，不得建议改值。
- **代码与标识符**：代码块、路径、接口名、命令、文件名、模型字段按原文保留，块内内容不进入审查。

遇到不确定的语义边界（删除之后还剩不剩原来的意思、引号里是什么、同一个词的不同用途），读 [编辑边界](references/editing-guide.md)；判断"该标到什么程度"可对照 [标注对照](references/examples.md)。两份都是按需参考，短文不必每次通读。

## 只标问题的输出约定（check_language 工具遵循）

- 每条问题必须给出：`section`（所在章节标题）、`quote`（原句片段，**逐字摘自草稿**，不许转述或缩写）、`issue_type`（上一节括号里的枚举值之一：`filler_opening` / `meta_transitional` / `redundancy` / `wordiness` / `credentialing` / `negation_defensive` / `translationese`）、`why`（由原文支持的具体理由）、`suggestion`（修改方向，不是改写文本）。
- `quote` 在草稿里找不到逐字命中即整条丢弃，所以摘引时不改动任何字符、标点与空格；`issue_type` 不在枚举里同样丢弃。
- 表达累赘与事实依据不足是两回事，不混用理由；缺数据、缺来源或前后矛盾属于独立审稿与数字核验（`check_draft`）的职责，语言审查不报。
- 不输出改写后的全文，不输出评分或"AI 含量"，不判断文章是不是 AI 写的。

## 两轮审查的流程约定（写稿分析师遵循）

**审查对象（正式产物，与 `check_language` 的 `is_reviewable_deliverable` 同一规则）**：所有由智能体写成、留在工作区里给人读的 Markdown——`drafts/` 下的草稿、`research/` 下的各类笔记（bullbear-quick、industry、valuation、delta、快讯、前瞻、异动、公告点评、专题各章节等）。**不审**：原始数据与机器文件（json、csv、xlsx、脚本）、`bg_data/`、`data/`、`lenses_work/`、`model_dump/` 下的抓取原文与中间数据、知识层 JSON 渲染出来的文件（thesis.md、agenda.md、verdicts.md 等）、`research/topics/conversations/` 机器渲染的对话纪要、核验侧车（.audit.md、.annotated.md、.language.md）、`published/` 归档稿（发布横幅使哈希不同且归档不可改，其语言审查以对应草稿为准）。

1. **第 1 轮**：初稿写完之后、**第一次独立审稿之前**（一次写完、不再改的笔记，写完后即做）。因 `check_language` 每次只看一节，写稿人在成稿后先通读全文，将跨章节重复的同一缺口、同一限定、同一改判条件合并或只保留最合适的一处（不影响结论的缺口：报告放 `## 附注`，推送稿放 `## 来源`），再调用 `check_language(draft_path=…, round=1)`，读 `<draft>.language.md` 清单，按清单修改（只改语言表达，不动事实、数字、术语、引用编号与判断强度），然后才提交独立审稿。
2. **第 2 轮**：内容定稿后——过独立审稿的文档在审稿修订循环结束、**提交最后一次独立审稿之前**（每次修订后同样先通读全文清理跨章节重复）；一次写完的笔记在第 1 轮改完后即复核。调用 `check_language(draft_path=…, round=2)`，按清单完成修改；**若稿子有改动，再调用一次 `check_language(round=2)` 复核**（同一 json 追加记录，使最后一条第 2 轮记录绑定终稿哈希）；然后做最后一次独立审稿与 `check_draft`。第一次独立审稿就 pass 时：第 2 轮照常进行；若第 2 轮改了稿，补一次终稿审稿重新绑定哈希，哈希未变则无需重审——上一条 pass 记录仍绑定当前稿。
3. `check_language` 返回错误（模型不可用、超时）时不算通过：不写侧车、不得跳过，重试或升级人工处理。
